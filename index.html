Case studies

A few problems I worked through in production, and the trade-offs behind each fix.

2+ min (timing out) → ~5 s

Speeding up a reward-eligibility query

Problem
A SQL Server stored procedure that checked multi-leg bets, and every leg inside them, against reward rules ran for over two minutes and regularly timed out.
Investigation
The execution plan showed correlated subqueries forcing row-by-row nested loops, with predicates that could not use the existing indexes.
Fix and trade-off
I pre-filtered the bets and their legs separately on indexed columns, then combined them with a LEFT JOIN. Adding another index was the obvious alternative, but the table was write-heavy and already carried many indexes, so I improved the query instead of slowing every write.

Frequent OOMKilled → stable

A memory limit that was too generous

Problem
A Node.js GraphQL service kept high memory usage and was frequently OOMKilled by Kubernetes.
Investigation
Using OpenTelemetry GC frequency and memory metrics, then verifying with tests, I found the V8 heap limit was set higher than the container's memory limit. V8 saw plenty of room and delayed full GC, so the container hit its limit and was killed first.
Fix
I set the heap limit to 80% of the container limit, leaving headroom for memory outside the heap. GC started running normally and the OOM restarts stopped.

Node.js · V8 · Kubernetes · OpenTelemetry

False alarms: ~every 2 weeks → 0

Telling a quiet evening from an outage

Problem
A traffic-drop alert fired about every two weeks, and almost always it was just a popular match ending. Correlating traffic with match data meant querying across databases on different machines, which our rules didn't allow.
Reframing
I didn't need the exact relationship — only whether a drop was local or global. Every sport is served by the same service, so a real failure takes all sports down together.
Fix
I monitored bet counts for the top ten matches of each sport, all from one database, and alerted only when every sport dropped together. A slope threshold tuned on historical data filtered out the gradual off-peak decline.

Design trade-off

Out-of-order events in a Kafka pipeline

Problem
When a new Bet Builder market opened together with its base odds, the Bet Builder data from a third party could arrive before the base odds existed.
Approach
The consumer stored an incomplete record; once the base odds were processed, an event on a separate topic let a backfill service complete it. Timestamp-based conditional updates meant older or duplicate events never overwrote newer data.
Trade-off
Odds are high-frequency state where only the latest value matters, so a failed update is corrected by the next one. We relied on alerts and a full-resync endpoint instead of per-message retries — for data that must not be lost, such as payments, I'd use bounded retries and a dead-letter queue.

Kafka · Eventual consistency · Idempotency
